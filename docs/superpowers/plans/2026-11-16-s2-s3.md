# S2 / S3 顺序实施计划

## 用户授权与边界

2026-11-16 用户明确要求 S1 完成开发后直接开发 S2、S3，之后统一人工验收。因此允许基于机器通过的前置候选继续开发，人工签收延后；这不表示 S1 已 accepted，也不授权合并 S1–S3。分别保留 Draft PR、独立证据和 manual_pending 状态。只在 S2 机器通过后实施 S3。

## S2

- 新增 Group / Replicate 管理和四阶段空容器视图；复用 S1 受控测试库，不初始化未知库。
- `experiment_tree({request})`：request action=list/create/rename/delete，assayId 必填；kind=group/replicate，id/parentId/name/requestId 按操作提供。
- response `{assayId, groups:[{id,name,replicates:[{id,label}]}], stages:[{id,label,scope}], replicateCount}`；stage id raw/processed/statistics/display，前两者 scope=replicate，后两者 scope=assay。
- 强制 assay 作用域，稳定 ID，事务/幂等和非空删除保护；样本数只来自 replicates，不因资产复制或关联变化。
- UI 在 S1 所选实验中进入“分组与样本”，显示分组/样本数和四阶段空态。浏览器 Mock 明确标注。
- 新增 s2_、@S2、真实临时库 IPC 验证；3组×6样本、重开库、跨 assay 失败、样本数不变量、空阶段与回归。

## S3（S2 机器通过后）

- 从现有只读拖入进入目标选择、确认、任务进度/取消/重试；固定阶段/样本作用域。
- Rust 执行流式复制和 SHA-256，源路径只保存在原生任务内；同卷 staging、不可覆盖 CAS、持久 job 状态与 SQLite 登记。
- 先明确 staging/commit/reconcile 状态机和故障断点，再实现；不能将 SQLite 事务冒充文件系统事务。
- s3_ 与 @S3 覆盖 100 文件、受控大文件、重复请求/字节、源变动、锁/路径竞态、取消/故障/恢复和源哈希不变。
- 不递归目录、不生产导入、不修改源、不解锁珍贵数据；S7 恢复演练门槛保持。

## 交付

每阶段分别更新执行规范、任务 JSON、报告与机器证据，提交堆叠 Draft PR；最后提供同一候选 EXE 的 S1–S3 人工验收步骤。未经用户签收不标记 accepted，不自动合并。
